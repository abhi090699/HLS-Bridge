Q1: Explain the architecture of your UVM-based verification environment.
What were the key components and how did they interact?

OVERVIEW:
The environment is a layered UVM testbench centered on cdn_pcie_hls_bridge_env.
Stimulus is owned by a virtual sequencer/virtual sequences; checking is owned
by a module-level monitor that fans VIP observations into predictors,
scoreboards, and an inbound posted order checker. Configuration is pushed
through env_config + uvm_config_db, with multi-domain resets coordinated by a
reset manager.

LAYER DETAIL:

1) Test layer (base_test.sv / test.sv)
   - Creates env, env_config, scenario, strap/link/dev_top configs.
   - Applies factory overrides (CXS driver, tlp2cxs, IDE config, policies).
   - Directed tests further override TLP types (UIOMRd/UIOMWr).

2) Environment layer (env.sv)
   Instantiates:
   - Clock env + reset envs (core, axi_dti, axi_msi, axil)
   - HAL CXS HLS envs: OB/IB × Posted/Non-Posted/Completion
   - AXI CXS HLS envs arrays [NUM_HLS_PORTS] for the same six classes
   - AXI-Stream VIP envs: HDR2LOG, Delivered Count, QoS, LTI, MSI
   - AXI-Lite master/slave + hls_bridge_regmodel + uvm_reg_predictor
   - HPA OB/IB trans envs (CIF TLP router + tag manager)
   - Optional DTI/ATS envs
   - Virtual sequencer + module monitor + reset_manager

3) Stimulus interaction
   vseq programs misc straps (flit mode, route_en, credits), then starts
   child sequences on the appropriate sequencer handles in the vsequencer.
   For QoS/credits/delivered progress, analysis FIFOs from monitor back into
   vsequencer let sequences react to DUT progress.

4) Checking interaction
   VIP passive monitors emit started/ended callbacks → TLM analysis FIFOs in
   cdn_pcie_hls_bridge_monitor → predictors (OB merge, LTI) → CXS/stream
   scoreboards and ib_posted_order_checker. check_phase demands empty queues.

5) Typical IB Posted path
   IB HAL CXS drive → DUT route to AXI/DTI/MSI → sink monitors → expected
   port_tr into order checker + data scoreboards → delivered-count retires
   expected entries → quietness wait in vseq → check_phase.

ASCII:
  TEST → ENV[ VIPs | trans(tag+router) | regmodel | vseqr | monitor ]
  monitor → predictors → scoreboards
          → IB posted order checker
  vseq ⇄ vseqr sequencers; monitor APs → vseqr FIFOs (credits/QoS/DC)

Q2: How did you integrate multiple protocol VIPs (CXS, AXI-Stream) into a
single environment? What challenges did you face?

OVERVIEW:
Each interface role is a separate UVC env instance, configured via config_db,
connected in connect_phase, and stimulated through one virtual sequencer.

CXS INTEGRATION:
- cdn_hls_env wrappers around Denali CXS VIP.
- Critical: direction CDN_HLS_TX vs CDN_HLS_RX must match whether TB drives or
  receives. Example: HAL OB posted = RX (observe DUT→PCIe); AXI OB posted = TX
  (drive client→DUT).
- Active + passive agent configs + optional cov collector cfg per path.
- Arrays for AXI-side ports.

AXI-STREAM INTEGRATION:
- cdn_axi_stream_vip_env for HDR2LOG, DC, QoS, LTI, MSI.
- Different transaction type (denaliStreamTransaction), so separate typed TLM
  FIFOs and generic stream scoreboards.

CHALLENGES & FIXES:
1) TX/RX confusion on HAL vs AXI — fixed by explicit config_db direction sets
   and smoke tests per path.
2) Width/port parameterization — HLS_PORT_DATA_WIDTH_ARR; runtime sizing in vseq.
3) End-of-test sync across many VIPs — quietness loops + CXS deacthint/STOP
   handshake (PCIE-19531), longer timeouts under backpressure.
4) Multi-reset domains — reset_manager discovers I_cdn_pcie_hls_bridge_reset
   implementers and flushes tags/FIFOs/sequences.
5) Metadata formats — unpack CXS UserControl into RO/idgroup structs for
   ordering; parse DC stream bytes for count/id_group.

Q3: What is the HLS Bridge IP? What was its primary function in PCIe Gen7?

OVERVIEW:
HLS Bridge (hls_bridge_top.v) is the bridge between the PCIe controller HAL
(CXS) and client HLS ports (plus optional DTI and MSI). It moves Posted,
Non-Posted, and Completion TLP streams in both Outbound and Inbound directions.

PRIMARY FUNCTIONS:
- OB: client HLS → HAL/PCIe
- IB: HAL/PCIe → AXI HLS ports / DTI / MSI (routing policies)
- Separate P/NP/CPL channels (ordering + FC)
- Credit limiting / backpressure behavior
- Delivered-count and QoS telemetry to software/HAL
- FM and NFM operation
- Configurable widths (128/256/512/1024) and multi-port
- IDE/TDISP participation when enabled

GEN7 ANGLE:
Flit Mode as first-class (KMAX_FLIT_MODE_SUPPORT, m_misc_flit_mode), wide
datapaths (Makefile 1024dp/fm/...), extended tags, IDE Gen7 defines
(HPA2_IDE_GEN7 influences route_en.ro_en in scenario), coverage_gen7.tcl.

Q4: Why UVM? Advantages over other methodologies?

OVERVIEW:
UVM matched the VIP ecosystem and the complexity of a multi-protocol,
multi-port Gen7 bridge.

ADVANTAGES WE ACTUALLY USED:
1) Factory overrides — specialize VIP driver/sequences/policies/TLPs without
   forking vendor code (base_test + directed tests).
2) Phasing — deterministic build/connect/run/check for many components.
3) config_db — one env_config programs dozens of agent paths.
4) TLM analysis — non-intrusive fan-out to predictor/SCB/order/coverage.
5) Virtual sequences — compose mixed IB/OB/reset/BP/register traffic.
6) Register layer — AXI-Lite adapter + predictor with auto_predict.

WITHOUT UVM: copy-paste VIP wiring, weak reuse across FM/width configs, harder
objection/drain semantics, no standard factory for directed UIO overrides.

Q5: CXS VIP with AXI-Stream VIP — compatibility issues?

OVERVIEW:
They coexist because the DUT exposes both a packet datapath (CXS) and
sideband telemetry/control (AXIS). Compatibility is about types, timing,
metadata, and flow-control models—not wire-level mutual conversion.

ISSUES:
1) Transaction types differ → typed FIFOs/scoreboards only.
2) Metadata packing (UserControl vs DC byte fields) must stay consistent with
   RTL definitions or order/DC checks false-fail.
3) Flow control: CXS credits (crd_lmt_if) vs AXIS ready/valid.
4) Clock/reset domains differ; checking is transactional after pkt end.
5) Same-cycle start/end races across forked monitor tasks — predictor uses
   wait_for_hash_zero_delay to stabilize.
6) End-of-test: both VIP families must be quiet; CXS needs deacthint/STOP.

Q8: Key challenges developing Gen7 PCIe verification environment?

1) Flit Mode vs NFM — packing, alignment, gaps, straps, rate floors.
2) Width matrix 128→1024 — TLPs/clk, AXIS sizes, legal constraints differ.
3) Multi-sink IB — one ordering model across AXI/DTI/MSI latencies.
4) Tag space growth — 8/10/14/UIO, exhaustion, CPL_TO.
5) Feature interactions — RO × BP × multiport × reset × IDE.
6) Sim cost — need sanity vs full matrix; COV optional; IMC merge.
7) Spec flux — TODOs in scenario (flit 00, RO constraints) show living ECO.
================================================================================
Q9: Handle different data widths (128/256/512/1024)?

Compile-time parameters (HLS_PORT_DATA_WIDTH_ARR, KMAX_DATAPATH_WD) select
build. env_config returns per-port width. vseq sizes HDR2LOG bytes = width/8
and special-cases 128-bit. Constraints force DW alignment 2 when 128b & 2
TLPs/clk; otherwise design currently 4 DW start align. Separate regression
builds (e.g. 1024dp/fm). Scoreboards compare full packet bytes; don't
hardcode width in checkers. Coverage merged per config with IMC options that
tolerate class-instance differences across builds.
================================================================================
Q10: Configuration management techniques?

Four layers:
1) parameters_cfg_pkg — structural (ports, widths, DTI/MSI/IDE/FM).
2) scenario — rand test intent (traffic, credits, flit, route_en, resets, BP).
3) strap/dev_top/link policies — device/port personality, BARs, speeds.
4) uvm_config_db + factory — per-agent programming and type specialization.

Runtime misc_if_api applies flit/route/tag straps after randomize. Regmodel
mirrors dbg controls consumed by order checker. This separation lets one TB
tree support many product SKUs without ifdefs everywhere in sequences.

Q11: UVM phases — how used in your environment?
================================================================================
OVERVIEW:
We used standard UVM phases with clear ownership: build creates, connect wires
TLM, run-time sequences/checkers execute, check proves queues drained.

TB DETAIL:
- build_phase (env): build_cfgs, optionally factory-override monitor→cov_monitor
  when coverage_enable, then build clk/rst/CXS/HDR2LOG/MSI/DC/QoS/LTI/AXI-Lite/
  DTI/reg/misc.
- connect_phase: reset_manager discovery; regmodel map↔AXI-Lite sequencer +
  predictor bus_in; OB/IB trans connects; vseqr sequencer handle binding;
  monitor analysis ports → vseqr FIFOs (delivered/QoS/credits).
- main_phase: vseq traffic; order checker / predictor forever tasks.
- check_phase: predictor is_balanced, order checker balance, SCB emptiness.
- Objections: sequences keep main_phase alive through drain/quietness waits.

Q12: Virtual sequencer coordinating multiple protocol sequencers?
================================================================================
OVERVIEW:
cdn_pcie_hls_bridge_vsequencer is a handle container + reset controller, not a
single protocol sequencer.

TB DETAIL:
Holds clk/rst sequencers; per-port OB AXI CXS P/NP/CPL sequencers; IB HAL CXS
P/NP/CPL; AXI-Lite M/S; HDR2LOG/DC/QoS/LTI stream sequencers; TLM FIFOs for
delivered TLPs/QoS/credits so sequences can pace on DUT progress.
Virtual sequences declare p_sequencer and start children on the right handle.
On reset/link-down it stops CXS/TLP sequences to avoid waiting forever for
completions that reset invalidated.

================================================================================
Q13: TLM-1 vs TLM-2 — which and why?
================================================================================
OVERVIEW:
TLM-1 = put/get/analysis (classic UVM). TLM-2 = generic payload/sockets
(SystemC-oriented). We used TLM-1 analysis ports/FIFOs exclusively for VIP
broadcast of completed packets to predictors/scoreboards/order checker because
it is non-blocking for the monitor, supports 1-to-many, and matches Denali VIP
callback style.

================================================================================
Q14: Clock domain crossing CXS vs AXI-Stream?
================================================================================
OVERVIEW:
Unit TB verifies transaction correctness across domains rather than claiming
full CDC formal sign-off.

TB DETAIL:
Separate reset envs for core vs axi_dti/msi/axil. Checkers consume packet-end
TLM events, not same-cycle signal assumptions. Quietness/timers absorb skew.
Credit/ready models create domain-local backpressure. True metastability bugs
are usually full-chip/gate-level; we stress with asymmetric ready and staggered
resets to catch functional CDC mismanagement.

Q15: Config mechanisms for different IP configurations?
================================================================================
OVERVIEW:
parameters_cfg_pkg (structure) + scenario (intent) + strap/dev policies
(device personality) + uvm_config_db (agent programming) + misc_if_api
(runtime straps) + regmodel mirrors (dbg enables).

This lets FM/NFM, widths, ports, DTI/MSI/IDE change without rewriting sequences.

Q16: Environment reusable across configurations?
================================================================================
OVERVIEW:
Arrays sized by NUM_HLS_PORTS; ifdefs for DTI/passive TB; factory overrides
instead of hardcoded types; constraints keyed off parameters (flit/DTI/IDE);
active/passive agents; coverage monitor swapped by factory when FUNC_COV.
Same env class serves many Makefile configs.

================================================================================
Q17: uvm_component vs uvm_object?
================================================================================
OVERVIEW:
uvm_component: hierarchy, phases, path-based config, reporting — env, monitor,
scoreboard, driver, sequencer, predictors, order checker.
uvm_object: create/destroy freely — TLP items, scenario, env_config, sequences.
Mixing them up breaks phasing or inflates memory (putting transactions in
component tree).

================================================================================

- cdnCxsUvmDriver → cdn_pcie_hls_bridge_cxs_driver (link-down behavior)

Q19: build_phase vs connect_phase?
================================================================================
OVERVIEW:
build creates components top-down (children exist after parent build returns).
connect wires TLM/virtual interfaces after children exist.
Connecting in build risks null handles; creating in connect breaks config/factory
timing and hierarchy conventions.

Q21: OB vs IB TLP traffic — verify both?
================================================================================
OVERVIEW:
OB = client→PCIe (drive AXI HLS, monitor HAL). IB = PCIe→client (drive HAL,
monitor AXI/DTI/MSI). Separate VIP envs, sequencers, predictors/SCBs per
direction and per P/NP/CPL class.

TB DETAIL:
OB checking emphasizes merge prediction + OoO-capable SCBs when multiport/DTI.
IB checking emphasizes per-port SCBs + posted order checker + DC/QoS.
Mixed tests fork both under one vseq while sharing credits/tags/resets.

Q22: Posted, Non-Posted, Completion — how verified?
================================================================================
POSTED: no CPL expected; IB order checker + posted SCBs; RO metadata matters.
NON-POSTED: tag_manager alloc/block/release; request SCBs; LUT context; timeout
/FLR release paths.
COMPLETION: tag match (8/10/14/UIO); split tracking; possible shuffle stress in
router; CPL SCBs; tag free when complete.

================================================================================
Q23: HAL-side CXS vs AXI-side HLS?
================================================================================
HAL-side: link/controller-facing CXS streams (single logical HAL P/NP/CPL OB/IB).
AXI-side HLS: client ports arrayed by NUM_HLS_PORTS with possibly different
widths, plus AXIS sidebands (DC/QoS/HDR2LOG/MSI).
Verification asymmetry: OB is many-to-one merge; IB is one-to-many route.

================================================================================
Q24: HLS ports — why dual?
================================================================================
Multiple clients or bandwidth aggregation; independent widths; inbound split
policies (port0/IDG/VC/TC/function/address/random). TB arrays all AXI-side
agents/sequencers/FIFOs/SCBs and covers splitting schemes in monitor.

================================================================================
Q25: TLP routing correctness across ports/CXS?
================================================================================
Scenario sets m_ib_target + m_hls_bridge_route_en. DUT/CIF router apply policy.
Monitor predicts dest into order-checker expected queue. Per-dest SCBs compare
bytes/metadata. Delivered-count must match retirements per id_group. Failures:
SCB mismatch, order error, or DC count error.

================================================================================
Q26: Flow of Outbound Non-Posted MRd to completion verification?
================================================================================
STEP-BY-STEP:
1) vseq selects OB NP / UIO read traffic.
2) HPA TLP item created (MRd/UIOMRd).
3) tag_manager allocates tag (or blocks if pool empty); tracks consumed.
4) bridge tlp2cxs adds metadata; drive AXI OB NP CXS port.
5) DUT presents on HAL OB NP; monitors capture AXI start/end + HAL end.
6) OB NP merge predictor → OB NP SCB compares predicted vs HAL actual
   (payload, UserControl, end_err).
7) Completion returns on CPL path; split tracker notes multi-CPL.
8) tag_manager matches tag, updates LUT, releases (or CPL_TO/FLR path).
9) End: wait_tags_empty + scoreboard quietness before pass.

================================================================================
Q27: Data integrity across OB/IB?
================================================================================
SCB payload compare; UserControl compare; end_err compare; order-checker byte
identity; DC vs expected queue; IDE when enabled; check_phase empty queues;
wait_tags_empty for outstanding NP; optional AXI error injection to ensure
error paths don't corrupt tracking silently.

================================================================================
Q28: PCIe ordering Posted vs Non-Posted?
================================================================================
IB posted-posted enforced by order checker unless RO/VC/TC disables.
NP identified by tags; completions may be OoO; OB SCBs enable OoO when
multiport/DTI (PCIE-20784). Full fabric posted-vs-NP passing tables are partly
system-level; bridge unit focuses on multi-sink posted + tag/CPL correctness.

Q29: Dual HLS-port configurations in verification?
================================================================================
Everything AXI-side is [NUM_HLS_PORTS]. Predictors take all ports (+DTI).
vseq loops ports for sideband sequences. OoO SCB when ports>1. Splitting
coverage proves distribution policy. Order checker expected entries carry
hls_port_num.

Q30: Gen7 traffic verification challenges?
================================================================================
Flit packing/gaps, 1024-bit beats, multi-TLP/clk, extended tags, IDE/TDISP,

Q31: TLP vs DLLP — verify both?
================================================================================
TLP: transaction packets — primary HLS Bridge scope (HPA TLP + CXS SCBs).
DLLP: link ACK/NAK/FC/PM — VIP/link ownership. Bridge TB abstracts FC as
crd_lmt_if credits rather than decoding raw DLLPs. Be explicit about scope in
interview.

================================================================================
Q32: Scoreboards for OB and IB TLP flows?
================================================================================
monitor creates cdn_pcie_tl_cxs_scoreboard per path with UserControl + end_err
compares. OB sets m_en_out_of_order_scb when multiport or single-port+DTI.
IB: per-port P/NP/CPL SCBs + optional DTI. Stream generic SCBs for
HDR2LOG/MSI/LTI/DC (DC OoO). Expected from predictors/HAL; actual from sinks
via analysis FIFOs.

================================================================================
Q33: AXI-Stream vs CXS — why both?
================================================================================
CXS = TLP datapath (SOP/EOP, credits, flits, UserControl).
AXIS = sidebands (DC counts, QoS, HDR2LOG, MSI, LTI).
Both required: correct TLP with wrong delivered-count still breaks software.

================================================================================
Q34: Multiple HLS ports — routing mechanism?
================================================================================
Inbound splitting schemes covered in monitor: FORCE_PORT_0, IDG/VC/TC based,
function based, address based, random. route_en gates policies. OB: per-port
inject + DUT merge; SCB often OoO because strict OB multiport order not
confirmed (commented predictor sort code).

Q35: Tag manager for Non-Posted — deep explanation?
================================================================================
WHY: NP needs unique tags; sequences shouldn't manually track CPL lifecycle.

WHAT IT DOES:
- Policies: ascending/descending/random/LRU-ish reuse
- Pools: available/consumed/discarded/flred/released-by-TO/FLR
- Blocks generation when exhausted (backpressure into stimulus)
- compl_lut_obj maps tag→request context
- Modes: 8-bit/UIO start 0; 10-bit init 256; 14-bit init 1024
- Reset: kill NP seqs, rebuild pools, clear LUT, fix semaphore
- End: wait_tags_empty (10us poll, 1000us warning timeout)
- CPL_TO path records m_released_tag_by_cpl_TO

This turns completion protocol into a resource allocator and prevents false
TB fails from premature tag reuse.

================================================================================
Q36: Split completions for large reads?
================================================================================
Multiple Cpl/CplD share a tag until byte count completes request.
monitor track_split_ob/ib_completion uses cpl_seen_map; when split and random
order among CPLs, samples cover_*_split_random_order.
Router may shuffle uio_cpl_trans_q to stress. Tag frees only when fully done
(or error/timeout). SCBs must accept multi-beat CPL per request.

================================================================================
Q37: Posted vs Non-Posted processing difference?
================================================================================
Posted: no tag, posted channel, ordering-sensitive on IB, fire-and-forget.
NP: tag alloc, may stall on tags+credits, LUT state, CPL path split/OoO/TO,
more end-of-test drain (wait_tags_empty).

================================================================================
Q38: Completion timeout scenarios?
================================================================================
If CPL never returns, CPL_TO error code releases tag into
m_released_tag_by_cpl_TO. Timers 10/100/1000us exist. Honest point: code has
TODO for dedicated functional coverage (vplan 2.11.2)—mechanism present,
coverage still hardening.

================================================================================
Q39: 10-bit vs 14-bit tags?
================================================================================
Larger outstanding NP capacity on fast links. TB modes select pool base/size.
CPL matching must use full vector (tag + t8/t9 + 14-bit scale), not [7:0] only.
Router debug prints show concatenated tag fields.

Q40: ATS translation requests?
================================================================================
ATS: device asks IOMMU for translations; ATC caches; invalidations keep
coherent. Here mainly DTI path: dti_ats_env, inv req knobs, force fault,
router IDO reserved on translation completions. Not every AXI-only config.

Q41: Role of monitor — enhancements?
================================================================================
Passive observer publishing transactions—never drives DUT.
Module monitor enhancements: multi-IF FIFO hub; owns predictors/SCBs/order
checker; CXS↔TLP conversion for QoS/split; APs back to vseqr; reset flush;
factory-swappable cov_monitor; inbound split coverage hooks.

================================================================================
Q42: Monitor vs predictor — both implementations?
================================================================================
Monitor: what VIP/DUT showed.
Predictor: given inputs+spec, expected outputs.
OB merge predictor consumes per-port ends, emits predicted HAL CXS to SCB
expected. IB path predicts delivered port_tr into order checker expected queue.
LTI ctag predictor similarly. Separating RM keeps SCB as pure compare engine.

================================================================================
Q43: TLM analysis ports and FIFOs?
================================================================================
VIP ap.write → fifo.analysis_export → checker fifo.get in forever task.
Benefits: decouple rates, avoid callback re-entrancy, fan-out, reset flush.
Examples throughout monitor and order checker (per-port AXI ended FIFOs, etc.).

================================================================================
Q44: Validate packet routing — checks?
================================================================================
Dest IF correct; payload/metadata intact (SCB); ordering vs earlier posted;
DC matches retirements; splitting coverage explains port choice; dbg disable
registers honored without false fails.

================================================================================
Q81: PCIe ordering rules — why important for Posted?
================================================================================
OVERVIEW:
Posted writes have no completion handshake, so ordering rules are what keep
producer-consumer relationships correct.

CLASSIC EXAMPLE:
Producer writes DATA then FLAG (both posted). Consumer waits for FLAG then
reads DATA. If FLAG passes DATA in the interconnect, consumer sees stale DATA.

RULE FAMILIES:
Strict, Relaxed Ordering (RO), ID-based (IDO), TC/VC independent orders.
HLS Bridge can deliver IB posted to AXI, DTI, and MSI with different latencies—
so multi-sink posted ordering must be explicitly checked
(ib_posted_order_checker.sv).

================================================================================
Q82: Strict vs Relaxed Ordering — how implemented?
================================================================================
STRICT: disable_ordering=0. On actual retire, any earlier same-id_group expected
posted still undelivered on another dest/port → uvm_error + tables.

RELAXED: UserControl.ro OR route_en.ro_en OR vc_en OR tc_en → disable_ordering=1;
log + sample cg_disable_p_p_order_check; no error.

TB NOTE: under HPA2_IDE_GEN7, scenario forces ro_en==1—know your default
stimulus mode in interview.

================================================================================
Q83: AXI, DTI, MSI interfaces — relation in HLS Bridge?
================================================================================
AXI HLS ports: primary client TLP CXS interfaces.
DTI: optional data-transfer path (ATS-capable).
MSI: interrupt messages on AXIS MSI slave.
QoS aggregates completion counts from AXI (+DTI+MSI) toward HAL (qos_spec.txt).
Order checker destinations: ROUTE_TO_AXI / ROUTE_TO_DTI / ROUTE_TO_MSI.

================================================================================
Q84: Order checking solution architecture?
================================================================================
DATA PATH:
monitor predicts IB posted delivery → m_in_exp_p_pkt_ended_af → ib_p_exp_q
actual AXI/DTI/MSI ended FIFOs → check_p_p_ordering
DC streams → handle_delivered_count deletes N matching entries

CONTROLS: checks_enable, coverage_enable, regmodel dbg_dis_* , RO disable
END: is_balanced in check_phase; tabular print_table for debug

================================================================================
Q85: Ensure ordering across AXI, DTI, MSI?
================================================================================
One expected queue tagged with dest_port + hls_port_num + id_group + data_bytes.
Any sink's actual retire searches expected and verifies earlier same-id_group
entries aren't stranded on other sinks (unless relaxed/disabled).

================================================================================
Q86: Data structures for order checker — multiple streams?
================================================================================
Queue of cdn_pcie_hls_bridge_ib_port_tr_delivered_s.
Per-port uvm_tlm_analysis_fifo for AXI actuals; single FIFOs for DTI/MSI/DC.
Match keys: dest, port, id_group, byte array compare.
id_group from UserControl or DC PacketData[1][3:1].

Q87: Verify ordering violations — what checks?
================================================================================

DC mismatch if delivered count ≠ matching entries found; coverage when check
intentionally disabled; check_phase fails if queue not empty.

Q88: Specific Posted rules implemented?
================================================================================

different dest/port still pending (strict).
MSI matched via payload bytes then ordered.
DTI act path always checks (disable_checking 0 in that task).
AXI respects RO/route flags.
Per-sink dbg registers can skip.

Gen7 path emphasizes ro_en. Different TCs can reorder when enabled.

================================================================================
Q91: ID-based vs TC-based ordering?
================================================================================
IDO: same requester ID ordered; different IDs may reorder.
TC/VC: ordering domains per traffic class/virtual channel.
Checker keys id_group; tc/vc enables relax strict multi-sink checks.

================================================================================
Q92: Out-of-order completions in order checker?
================================================================================

OoO SCB flags. Do not conflate CPL reordering with posted multi-sink rules.

================================================================================
Q93: AXI vs DTI vs MSI protocols — why together?
================================================================================
Different software-visible services: bulk TLP (AXI HLS), DTI path, interrupts
(MSI). Bridge routes IB posted among them; ordering + QoS must consider all
three, so one checker spans all sinks.

================================================================================
Q94: Predictor for posted packets?
================================================================================

OB: merge predictor feeds HAL posted SCB expected from multiport AXI/DTI ends.
Different predictors for different problems (route/order vs merge/data).

================================================================================
Q95: Relaxed Ordering vs ID-based Ordering?
================================================================================
RO: TLP attribute allowing certain posted-posted passing.
IDO: attribute/mode allowing reordering across different IDs.
Related relaxations, not identical. Our checker models RO (and tc/vc enables)
via disable_ordering; still scopes comparisons by id_group.

================================================================================
Q96: Ordering when packets take different paths?
================================================================================
Exactly the ib_posted_order_checker problem: one expected timeline, multiple
actual path observers, error if a later path retires before earlier different-
path same-id_group posted is delivered.

================================================================================
Q97: Ordering vs coherency?
================================================================================
Ordering: PCIe transaction visibility rules.
Coherency: cache/memory consistency (CPU/CXL domain).
Bridge TB verifies PCIe ordering across sinks, not full system cache coherency.

================================================================================
Q98: Ordering across interfaces with different latencies?
================================================================================
Event-driven checks on retire, not fixed cycle budgets. DC stream confirms
batch drains. Under BP, extend simulation quietness. Tables show which sink
got ahead.

================================================================================
Q99: Posted vs non-posted ordering rules?
================================================================================
Posted-posted strongly ordered unless RO/IDO/TC relaxations.
NP can pass posted in many PCIe cases; completions have separate rules vs
posted. Our dedicated checker emphasizes posted-posted multi-sink.

================================================================================
Virtual sequencer heterogeneous handles; virtual sequence starts typed children
on each. Never send CXS items to AXIS sequencer.

================================================================================
Q168: uvm_analysis_port vs uvm_analysis_export?
================================================================================
See Q51 — port broadcasts; export receives; FIFO provides export+get.

================================================================================
Q169: Implement reference model in UVM?
================================================================================
Transaction-level components: OB merge predictors, LTI predictor, IB route
prediction into order checker, tag LUT, AXI-Lite reg predictor. Spec
abstraction—not cycle-accurate RTL clone.

================================================================================
Q170: uvm_reg vs uvm_reg_field?
================================================================================
Register object vs bitfield inside it. Order checker reads mirrored dbg fields
via hls_bridge_regmodel hierarchy.

================================================================================
Q171: Register backdoor access?
================================================================================
peek/poke HDL path for speed/setup; frontdoor AXI-Lite sequences prove bus path.
Note DTI map check_on_read=0 vs HLS bridge check_on_read=1 in env connect.

================================================================================
Q172: uvm_resource_db vs uvm_config_db?
================================================================================
config_db is convenience API with component context over resources—what
env_config uses. resource_db is lower-level.

================================================================================
Q173: Phase jumping in UVM?
================================================================================
Jumping run-time phases is rare/dangerous with undrained TLM. We use explicit
reset_manager + component reset APIs instead.

================================================================================
Q174: Default table printer vs custom?
================================================================================
Default uvm_object.print tabular; custom print_table/print_row for order queue
debug readability.

================================================================================
Q175: Callback mechanisms in UVM?
================================================================================
uvm_callback / VIP callbacks to inject errors or tweak transactions; also
axi_slv_cb_monitor; factory overrides as alternative specialization.

================================================================================
Q176: rand vs randc?
================================================================================
See Q77.

================================================================================
Q177: $cast vs dynamic casting?
================================================================================
$cast(tgt,src) safe; returns 0 on fail. Needed for p_sequencer / base handle
downcasts. Hard cast can fatal.

================================================================================
Q178: queue vs dynamic array vs associative?
================================================================================
queue[$]: push/pop ordered (ib_p_exp_q, tags).
dynamic[]: sized arrays.
associative[key]: sparse maps (cpl_seen_map, released_tag_by_cpl_TO).

================================================================================
Q179: inside vs dist?
================================================================================
inside: membership. dist: weighted membership. Used on TLP types and credits.

================================================================================
Q180: solve before vs if/else constraints?
================================================================================
See Q79.

================================================================================
Q181: always_comb vs always_latch?
================================================================================
always_comb: combo, latch-free if complete.
always_latch: intentional latch. RTL style in qos/delivered modules.

================================================================================
Q182: struct vs union?
================================================================================
struct stores all members; union overlays bits. Packed structs for metadata
(cdn_pcie_hls_ib_p_np_metadata_s).

================================================================================
Q183: logic vs bit?
================================================================================
logic 4-state (X/Z); bit 2-state. TB flags often bit; HDL-facing logic.

================================================================================
Q184: $random vs $urandom vs $urandom_range?
================================================================================
Prefer $urandom / $urandom_range (seedable SV). $random legacy signed 32-bit.

================================================================================
Q185: @(posedge clk) vs wait(clk)?
================================================================================
posedge = edge. wait(clk) = level true—not equivalent; can miss edges. Use
posedge/clocking blocks.

================================================================================
Q186: PCIe Gen5 vs Gen6 vs Gen7?
================================================================================
Gen5: 32 GT/s PAM4.
Gen6: 64 GT/s, Flit Mode first-class, stronger flit CRC/FEC.
Gen7: next-rate evolution; TB has Gen7 IDE defines, coverage_gen7, FM straps,
1024-bit configs.

================================================================================
Q187: Flit Mode — when used?
================================================================================
Gen6+ links in flit mode—fixed flits carrying TLPs with flit CRC/FEC.
Enabled when KMAX_FLIT_MODE_SUPPORT; scenario misc mode 2'b10.

================================================================================
Q188: 10-bit vs 14-bit tags?
================================================================================
See Q39 — larger outstanding NP; match full tag vector.

================================================================================
Q189: AXI vs AXI-Stream?
================================================================================
AXI: addressed R/W + responses (reg path).
AXIS: streaming valid/ready/data (DC/QoS/MSI/HDR2LOG).

================================================================================
Q190: CXS protocol vs AXI-Stream?
================================================================================
CXS: packetized HLS/PCIe stream with credits, SOP/EOP, flits, TLP packing
(Denali CXS / denaliCxsTransaction).
AXIS: simpler streaming sidebands. Different checkers/FIFOs.

================================================================================
Q191: Posted vs Non-Posted?
================================================================================
Posted: no completion. NP: needs completion/tag. Drives entire checker/tag
architecture difference.

================================================================================
Q192: PCIe flow control mechanism?
================================================================================
Per-VC credits PH/PD/NPH/NPD/CPLH/CPLD; UpdateFC DLLPs on link return credits.
Bridge TB models via crd_lmt_if header/payload/cntl + initial credits in
env_config—DLLP abstraction at unit level.

================================================================================
Q193: TLP vs DLLP?
================================================================================
See Q31.

================================================================================
Q194: ATS in PCIe?
================================================================================
Address Translation Service with ATC + invalidations. DTI ATS env + scenario
inv/fault knobs when enabled.

================================================================================
Q195: SR-IOV vs MR-IOV?
================================================================================
SR-IOV: multiple VFs on one PF in one root complex.
MR-IOV: multi-root/multi-host sharing.
This TB emphasizes HLS ports/functions/VCs more than full MR-IOV topologies.
